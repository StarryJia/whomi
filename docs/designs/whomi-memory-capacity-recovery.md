# 记忆生成容量恢复

本次为已授权的日常修错。基线为 main 的 9982c75；修复分支为 codex/fix-memory-capacity。2026-11-11 用户确认：初始批次同时考虑输入与输出上限，超限时缩小失败批次，保留进度与断点，不修改全局模型设置。

## 问题与行为

原流程按可用输入长度分片，输出额度较小时仍可能装入过多原文。模型返回 length 后，未结束的 JSON 被当作文稿格式错误。

已实现的恢复路径：

- 新任务的原文、归并和成稿材料预算取输入剩余额度与输出额度估算的较小值。输入预算沿用系统提示、输出预留和安全余量；输出预算暂按最大输出 token 数的四倍字节限制材料。这是保守估计，不是精确的 token 换算或服务商真实上限探测。
- 只对明确的输入容量错误及输出截断缩片。原文按消息或字符分成两段，归并按事件或事件文字分成两组；失败节点最多缩分八层，单段不足 128 个 UTF-16 代码单元时停止继续切分。字符边界不会拆开表情字符的代理对。
- 失败决策在发送子批次前保存；已完成子批次独立提交。原消息只在最后一段完成后计入进度。归并节点包含材料摘要标识，避免复用另一组的结果。
- 成稿超限先压缩已保存的事件材料再试，最多进行三轮容量恢复；归并最多八层且必须缩短材料。模型不再缩短材料时保留断点并报告失败。
- 网络、权限、一般文稿格式和证据错误沿用原错误处理，不作为缩片依据。原有成稿格式纠正重试保留。
- 兼容旧版分片及已保存归并节点；旧任务保留原分组预算。新容量预算和恢复决策仅存于分析任务，不写入模型配置或用户设置。
- 保留每次实际请求的用量，包括超限失败请求，不把缩片后的请求覆盖到前一次用量。

示例数据：第 1 批完成，第 2 批有一条 1400 字符消息且输出被截断。程序把第 2 批分为两段 700 字符；第一段完成后退出，重新打开只请求第二段，再继续第 3 批。第 1 批与第 2 批第一段不重复请求，第 2 条原消息在两段都保存后才计入进度。

## 代码与验证

- `electron/main/memory-recovery.ts`：任务级预算、持久化节点及原文缩片。
- `electron/main/memory-generation.ts`：原文、归并、成稿恢复调度。
- `electron/main/ai-service.ts`：恢复预算、保存断点及用量、识别截断。
- 模型运行器保留明确的输出截断信号，不猜测任意解析错误的原因。

失败测试先复现了四类问题：降低输出上限不影响初始批次、输入拒绝或输出截断后不缩片、重启后不能恢复细分批次、归并和成稿容量失败不能继续。随后逐项实现并验证。

验证结果：

- 完整后端测试：561 项通过。
- 完整前端测试：574 项通过。
- 前后端类型检查、网页构建、桌面构建通过；差异空白检查通过。
- 独立审查提出的三个问题均已先复现再修复：分析断点超过 32,768 字符时可继续保存与恢复；普通对话截断后保留失败重试状态；合并消息拆片后编号只对应该片正文。
- 分析断点字段上限调整为 16,777,216 字符；普通对话的断点上限保持 32,768 字符。原文边界保存在进程内弱引用表中，重启时由同一原文重新构造，不进入模型请求。
- 完整桌面测试首轮：48 项通过、2 项按条件跳过、1 项失败，耗时约 512 秒。失败项为 `tests/desktop/reading-polish.spec.mjs:52` 的 `reading polish: fixed content, history, model identity, copy, retry and narrow windows`。
- 随后单独运行 `reading-polish.spec.mjs`，该文件的两项测试全部通过，耗时 40.3 秒。未修改阅读界面代码；首轮失败未再次复现，原因未确定，因此不将首轮完整套件描述为全部通过。
- 跳过项为 `memory-capacity-upgrade.spec.mjs` 和 `upgrade.spec.mjs`，两项均需指定旧版或新版安装包路径及升级阶段。旧版记忆断点的逻辑兼容性已由后端测试验证，安装包升级路径本轮未验证。

本地依赖在先前合并后尚未同步；验证时从另一工作区恢复了与锁文件版本一致的安装副本，并执行既有 virtua 补丁脚本。依赖声明和锁文件未变。

验证只使用合成会话、本机模型服务及临时数据库。尚未用真实服务商重新处理最初的 14,639 条会话，也未改动该资料库；真实模型的提取质量与实际请求成本仍需使用时观察。
