# 界面设计、实现与审查的必用技能

适用工单：I01、I05、I06、I07，以及后续独立计划 Q00、H00。每个工单必须在对应阶段使用 impeccable、ui-ux-pro-max、design-review，并保留各自证据。纯后端 I02—I04 不增加这项要求；图片生成仍使用 design-shotgun。

当前只有静态设计图与工单准备，尚未完成对应页面实现或真实运行页面审查。静态图获批不等于 design-review 通过。Q00、H00 当前只安排后续计划，不因此开始功能开发。

## 三项技能的用途与证据

| 必用技能 | 使用阶段与要求 | 必须保留的证据 |
|---|---|---|
| impeccable | 设计和实现阶段读取产品与设计约定，遵守用户选定图、已确认交互和既有组件系统；优化细节不能擅自替换已选方案 | 使用的选定图路径、适用状态、既有设计依据，以及设计或实现的对照记录；实现后附对应尺寸的真实页面截图 |
| ui-ux-pro-max | 核对当前页面的具体交互、表单反馈、键盘与焦点、对比度和桌面窄窗表现；按 Electron 桌面应用及 React 组件上下文筛选建议，不照搬移动端导航、触控尺寸或断点规则 | 具体检查场景、采用的适用建议、窗口尺寸、操作步骤和结果；不适用或未验证项写明原因 |
| design-review | 页面实现后审查真实运行页面，并与选定图及相同尺寸的实现截图比较；发现问题后修复，再复查受影响状态 | 审查记录、运行环境与尺寸、真实截图、发现的问题、修复前后对照和复查结果；无法访问或未运行的状态明确标为未验证 |

## 执行顺序

1. 设计时使用 impeccable 保持既有界面系统和已选图约束，使用 ui-ux-pro-max 检查本页交互；需要新增或修改设计图时继续使用 design-shotgun，并按已约定的逐页流程确认。
2. 实现时再次按这两个技能核对当前页面与状态；仅已选图的对应状态进入实现，不能把正常态批准扩展为全部异常和窄窗布局。
3. 有真实运行页面后使用 design-review 审查。记录页面、构建或代码版本、窗口尺寸和操作步骤，修复后在相同条件下复查；静态生成图只作为对照基准。
4. 工单附三项技能证据与未验证清单。纯规划工单应写明哪些记录已完成、哪些由后续实现工单交付，不能为了补审查记录提前开发功能。

虚构验收场景：用户点击那次汇报准备，原文弹窗定位十月三日的证据。impeccable 对照已选 V2 核对弹窗和按钮布局；ui-ux-pro-max 核查键盘焦点、证据对比度及窄窗关闭操作；页面实现后，design-review 在实际运行窗口中检查定位和关闭恢复，保存发现问题与修复后的截图。只看到 V2 静态图时，上述实际交互仍记为未验证。

准备这些工单不触发 design-review 的提交、暂存或发布流程；后续技能执行仍遵守用户授权的任务范围与仓库约定。
