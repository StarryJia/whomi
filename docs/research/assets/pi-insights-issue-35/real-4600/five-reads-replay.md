# 五处原文回查的离线复例

真实模型顺读到第 526 条后，一次请求回看五处已读原文。第一处取得了第 1 至 17 条，其余四处都返回容量不足。随后 Pi 压缩了上下文，模型交出一份覆盖不完整的候选稿。暂停前没有再次请求这四处原文。正式任务依用户要求暂停，保留的覆盖为 526/4,600。[原始工具轨迹第 48 至 56 行](tools.jsonl#L48) · [重开后的进度](reopened.json)

重放使用同一份合成聊天和同样的五次定位，所有定位的向前条数均为 0。第 27 次请求的已知输入、输出分别为 8,922、384 个词元。应用的输入上限为 12,000，扣除这次推理用量及 128 的余量后，本次取文可用 2,566。应用按整个取文回包的字节数保守估算占用。测试启动真实 Pi 运行库，由本机回环服务重现同一轮的五次工具调用与用量回执。[归档合成原文](../4600/source.txt) · [可执行回归](../../../../../tests/backend/pi-insight-responses-resume.test.ts)

原来的第一处回包占 2,517 字节，此时只余 49，第二处连一条记录都无法容纳。修复后，每个调用按当前剩余容量及剩余调用数分配篇幅，较短的回包为后面的调用留下更多容量。这五个回包合计 2,534 字节，均包含请求定位的原文。回归测试还沿各自的后续游标取完窗口，确认五处回读均保持 526 条唯一覆盖。

只有一次取文时，该调用可使用当次全部剩余容量。可用容量为零时，五个调用均返回容量不足和空的来源集合，等待压缩后重试。上表只验证这五处原文的获取与分页，未生成新的长报告。[单次取文与超长分片回归](../../../../../tests/backend/insight-reader.test.ts)

在仓库根目录运行 `npm run test:backend -- tests/backend/pi-insight-responses-resume.test.ts -t "第 27 次请求"` 可重放此例。

## 均分后长消息放不下时的重试

另一个离线合成复例只含两条消息。#1 是 6,000 个「到」字，#2 是一个「好」字。Pi 同轮回查两个编号，余量共 328 字节。#1 最少需要 189 字节才能返回一个字和分片游标，均分只得 164，#2 的完整回包需 139 字节。工具告诉模型保留顺读游标，下轮按原参数单独重试。回环测试按 #1 再查，沿其分片游标拼回全部 6,000 字，最终唯一覆盖为两条。每次实际发出的取文调用只读一次。

运行 `npm run test:backend -- tests/backend/pi-insight-responses-resume.test.ts -t "328 字节"` 可检查这次恢复。模型自行决定是否按提示重试。
