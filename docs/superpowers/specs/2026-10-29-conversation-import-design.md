# Whomi 桌面后端与会话导入设计

- 日期：2026-10-29。
- 状态：设计草案，待用户审阅全文；方向已确认，不代表已经授权按本文所有细节编码。
- 范围：首个后端里程碑，交付桌面运行、常规导入、本地持久化与会话阅读。模型分析与其余完整业务另行设计。
- 基线：用户确认继续使用 `main`；编写前检查工作区、分支与跟踪关系，执行 `git fetch --all`、比较 `HEAD...origin/main` 并执行 `git pull --ff-only`。本次基线为 `0822624`，领先与落后均为零，工作区原本干净。
- 当前实际能力：只有 React、TypeScript、Vite 前端；选择文件尚不解析或保存，正式入口没有真实会话。本文除现状与核查证据外，均为待实现设计。
- 约定：所有 `m1`、`c1` 等标识及示例对话均为虚构示例。本地样本只记录结构性核查结果，不收录正文、名称、账号或私人路径。

## 1. 目标与范围

用户安装桌面程序后，可以选择文件或主动指定的导出目录，在本机导入受支持格式；导入成功后能重启应用继续阅读，并从稳定消息标识定位原文。导入不调用模型，不自动分析。

例如，用户导入同一联系人在两台电脑上导出的记录。第一次得到 `m1、m2、m3`，第二份只有 `m2、m4`，最终保存 `m1、m2、m3、m4`，原 `m2` 内容不变。

### 1.1 用户已确认的决定

| 事项 | 决定 |
|---|---|
| 产品与运行层 | 本地优先桌面程序，采用 Electron，沿用现有 React 前端 |
| 正式业务存储 | 一个 SQLite 数据库、一张共享消息表，通过整数会话编号关联 |
| 查询与写入 | 分页读取，按批次解析与暂存，为会话、时间和消息编号建立必要索引 |
| 数据模型 | 自定义 whomi 模型，借鉴 ChatLab，不照搬其交换文件或数据库结构 |
| 复用路径 | 优先引入 ChatLab 解析器集合，其他业务模块按需另行评估，后续独立维护解析器 |
| 导入行为 | 增量追加；同一来源会话范围内原始消息标识相同则跳过，不比较、覆盖正文或保存修订 |
| 缺失记录 | 新文件缺少旧消息时不删除本地旧消息 |
| 失败隔离 | 先暂存校验，再按会话使用事务提交；提交前失败不留下半份正式会话 |
| Spark | 不作为画像汇总输入；来源会话删除后 Spark 可保留，对应原文引用失效 |
| 人工智能导入 | 仅保留后续实验性方向，本轮不调用模型、不生成或执行转换脚本 |

“重复标识不处理”约束已有消息本体。导入批次仍可增加重复数量统计，不修改旧消息、旧消息显示名称、旧消息引用或附件。

### 1.2 本文提出的工程选择

以下选择由设计者提出，随全文审阅确认，不冒充用户此前逐项同意的要求：

- 首个可验证平台为 Windows，匹配现有开发环境；代码保持可移植，macOS、Linux 的安装包与签名不纳入本里程碑验收。
- 后台任务使用独立的 Node.js 运行进程，集中持有正式数据库写连接；主进程只协调窗口、文件选择、授权与任务生命周期。
- 一个导入任务串行提交各个会话；某个会话失败不撤销已成功会话，继续处理其他可处理会话。
- 目录导入先显示候选会话与范围，用户确认后开始；来源定位不清时先解决歧义，禁止凭标题静默合并。
- 缺少稳定消息标识的格式可以首次导入；同一源文件的相同记录可安全识别。不同文件之间的自动增量合并若无法证明同一消息，则暂停该会话并说明需要的操作，首期不以正文相同直接去重。
- 未知消息类型保留为 `unknown`，不静默丢弃；必要字段无法表达且影响身份、内容或顺序时，该会话校验失败。
- 本轮只生成消息数量、可用时间范围、成员数量等导入摘要；本人词频、中文分词和统计页面仍属后续产品里程碑，未被取消。

### 1.3 非目标与失败标准

本轮不实现微信数据库解密或账号采集、后台自动发现、云端存储、多设备同步、模型分析、画像计算、完整 Spark 持久化、反馈业务、人工智能转换和跨平台发布流水线。

会话删除的引用语义纳入存储约束；管理菜单、置顶、重命名、完整删除管理不是本导入里程碑的附带功能。不得为了加入这些入口扩大开发范围。

不可接受：覆盖重复消息；把另一台电脑缺失的记录当作删除；把同名的人或会话自动合并；失败后留下可见的半份数据；启动或导入触发模型；将私人正文放进日志、测试夹具或仓库。

## 2. 方案比较与选择

### 2.1 产品复用范围

| 路径 | 现有能力与剩余工作 | 结论 |
|---|---|---|
| 直接采用或整体改造 ChatLab | 已有导入和阅读，但仍需替换产品体验并增加 whomi 的自我理解业务；会引入超出本阶段的运行与业务模块 | 已讨论，不选择整体改造 |
| 基于现有 whomi 前端复用解析器 | 保留已经完成的前端，接入现成格式模块，编写统一转换、增量与存储层 | 用户选择 |
| 从零逐个平台实现全部解析器 | 不引入上游实现依赖，但需重新维护大量格式知识和样本 | 不作为默认路径；只补实际差异 |

例如，直接复用解析集合后，Telegram 和微信输入都交给统一转换层，后续阅读同一套 whomi 消息，而非为每个平台复制一套数据库和阅读页面。

### 2.2 运行层与数据库布局

Electron 与现有前端和解析器的 Node.js 文件依赖容易衔接，用户已选择；Tauri 仍可承载前端，但复用当前解析器时还需解决 Node.js 运行或迁移，当前不承担该额外工作。

共享消息表、每会话一张表、每会话一个数据库均已讨论。共享表便于 whomi 的跨会话身份关联和后续查询；独立数据库便于会话级迁移与隔离，不能声称其所有操作都更慢。用户选择共享表。

例如，阅读一个会话时由会话编号定位索引范围，只获取一页；增加会话不增加新消息表。共享数据库的写操作需要排队，分表但仍在同一数据库内不会改变这一点。

## 3. 证据与兼容范围

### 3.1 已核查上游

- ChatLab 参考提交：`f19beeadda27bd57eedc1bfbe75e7ed1b9e86833`。本轮阅读的是源码，不是运行兼容性证明。
- 该版本注册 14 个格式模块：ChatLab JSON、ChatLab JSONL、shuakami QQ 导出及其分块格式、WeFlow、echotrace、DiscordChatExporter、Telegram 全量及单聊天导出、WhatsApp 文本、QQ 文本、Instagram、Google Chat Takeout、LINE 文本。
- 解析包为仓库内私有包，依赖共享类型、原生解析包和流式 JSON 库，不能假定为已经发布的独立依赖。
- 原生解析加速有可选加载与 TypeScript 回退路径；具体格式仍需逐项核对，不能把整个桌面运行包作为解析器的必要依赖直接引入。
- ChatLab 格式规范为 `0.0.2`；JSON 和 JSONL 是文件组织形式，不是本地数据库结构。

首版的复用目标覆盖该格式集合，不退回只做 SIWX。最终“支持”清单必须按同一个验收合同证明；模块被注册、上游测试通过或文件能显示正文，都不等于 whomi 已完整支持。存在阻断时，在实现计划中列明，不静默缩减用户确认的复用目标。

### 3.2 用户实际样本核查

用户主动指定的 SIWX 导出目录内有一个会话 JSON、一个清单和两张图片。会话文件约 11.1 MB，包含 14,715 条消息、两个发送者、8,467 条标记为本人发送的消息、408 个非空引用对象。14,715 个原始消息标识均非空且在该文件内唯一，声明消息数与实际数量相同。

结构为 `exportInfo + session + messages`，不是 ChatLab 标准的 `chatlab + meta + members + messages`。它能匹配上游 echotrace 识别条件，该模块复用 WeFlow 解析逻辑；不能由此推断 SIWX 的开发来源或认定完整兼容。

已发现必须修正的差异：

1. SIWX 使用 `localType`、`typeName`，共享上游解析路径读取 `type`；whomi 必须专门映射，不把能导入等同类型正确。
2. 样本 `quote` 具有内容、名称和时间，没有可靠目标消息标识，保留引用摘要而不强行关联。
3. 来源导出者账号与本人消息使用的账号有后缀差异。身份确认必须基于明确映射，不制定任意去后缀规则。
4. 样本没有 `mediaFile` 字段。两张图片不证明每条图片消息都附有可读取的媒体。

不得把该私人样本作为必须存在的自动化测试路径。使用自行构造的最小虚构记录验证同样结构；获授权的本地人工验收只输出数量与差异类别。

## 4. 桌面运行结构

### 4.1 职责

| 部分 | 职责与限制 |
|---|---|
| React 界面进程 | 展示选择范围、进度、结果和消息页；不持有数据库连接，不接收执行任意文件操作的能力 |
| 预加载桥接层 | 暴露类型明确的进程间通信方法，不向页面开放通用执行接口；进程间通信下文称通信桥 |
| Electron 主进程 | 窗口、应用生命周期、系统文件选择、来源访问凭据、后台进程启停 |
| 后台数据进程 | 格式识别、解析、转换、校验、暂存、事务提交、数据库迁移与查询 |
| 正式数据库 | 由本地业务层统一管理；前端只能通过业务方法读取分页结果 |

上下文隔离保持开启，页面不启用 Node.js 通用访问。拖放或选择只授权本次来源；后续任务使用不可伪造的来源句柄，不允许页面传入任意路径或数据库查询语句。

例如，界面请求读取会话 `c1` 的前一页，后台验证本地会话编号后执行固定查询；界面不提供可执行的数据库文本。

### 4.2 生命周期与平台

正式资料放在 Electron 提供的用户数据目录，生产与开发资料隔离，不写仓库或安装资源目录。正式业务数据库可命名为 `whomi.db`；临时暂存可使用单独临时文件或临时数据库，不构成第二份正式资料库。

数据库在数据进程启动时迁移并检查兼容版本，页面打开后读取真实会话列表。后台退出或异常时，当前请求返回可重试错误；重启后回收中断任务的暂存区并根据正式提交记录恢复结果，不自动扫描用户来源目录或自动重新导入。

例如，应用在正式提交之后、结果通知之前退出，重启后仍应显示该次已保存会话，不能因通知丢失把它当作未保存。

具体 Electron 版本、SQLite 驱动、打包工具与后台进程启动方法由实施计划选定并固定，要求兼容桌面内置 Node.js 运行时；不能仅凭开发机的 Node.js 版本判断原生模块兼容。

## 5. Whomi 自定义数据合同

文件输入合同、解析器输出合同和正式数据库结构独立版本化。首期建立内部模型 `v1` 和数据库结构版本 `1`，不为统一内部结构而要求用户先转换文件，也不附带开发新的 whomi 导出格式。

### 5.1 实体与关键字段

下表定义字段含义与约束，不是要求实现者逐字照抄表名；具体列类型、方法签名和迁移文件由实施计划冻结。

| 实体 | 必须表达的信息与约束 |
|---|---|
| 会话 | 不复用的本地整数编号；来源平台；可空的来源会话标识；来源账号范围；私聊、群聊或未知；原始名称与独立显示名称；创建时间 |
| 来源账号 | 本地整数编号；平台；原始账号标识；来源标识稳定性；展示名称。不同平台或未证明相同的账号不合并 |
| 会话成员 | 会话与账号的关联、会话内名称；发送时名称在消息上单独保存，后续改名不改写旧消息 |
| 消息 | 不复用的本地整数编号；会话编号；发送者编号或明确的系统发送者类别；发送时名称；可空的标准时间；顺序键；消息类型；文本；可空的原始消息标识 |
| 消息来源 | 本地消息、导入批次、源文件指纹、解析器标识与版本、来源记录位置；不使用文件名作为唯一身份 |
| 引用 | 所属消息；可空目标消息编号；来源目标标识；摘要与时间等已提供信息；已关联、未解析或目标不可用状态 |
| 附件描述 | 所属消息、媒体种类、来源提供的定位信息、可用状态；没有文件时不构造媒体内容 |
| 本人确认 | 会话成员与确认状态；来源提示与用户确认分开；支持同平台稳定账号在无冲突时复用确认 |
| 导入任务与会话结果 | 任务编号、来源与解析器版本、状态、总数、新增、重复、异常与警告、提交时间；每个会话独立结果 |

消息类型采用 whomi 的语义值：`text`、`image`、`audio`、`video`、`file`、`sticker`、`link`、`location`、`reply`、`forward`、`system`、`unknown`；其他上游类型保留原始类别与必要扩展数据，不把不能表达的类型伪装成文本。新增语义值必须有版本兼容规则。

例如，SIWX 的微信类型数字与 ChatLab 数字不共享含义；映射为 whomi 的 `image` 后仍保留来源类别，后续可以修正映射而不猜数字来源。

### 5.2 时间、文本和顺序

- 内部标准时间为自 Unix 纪元起的毫秒整数，允许未知；原始精度、时区或无时区状态按需要保留。仅有本地时间且无法确定时区时不得猜测绝对时间。
- 正文保留来源提供的有效文本与换行，不自动裁剪首尾空白。显示占位与原文分开；空正文、未知类型和系统事件不静默丢弃。
- 有标准时间时按标准时间和稳定消息编号提供确定顺序；源记录顺序单独保留。时间未知的记录以明确的来源顺序展示，不能伪造日期参与时间统计。
- 仅保留重现原文与映射所需的扩展字段，不默认在每条消息保存整份重复原始对象；需要保留的 `rawContent` 若与正文不同，则明确保存用途与读取权限。
- 稳定本地消息编号在重复导入、显示名称修改和分页变化后不变；删除后不复用旧编号，不用数组下标充当持久引用。

例如，同一秒连续发送两条“好”，保留两个原始消息标识与两个本地编号，不根据文本和时间把它们合并。

### 5.3 身份与会话归属

格式适配器必须声明账号、会话、消息标识的作用范围和稳定性。标识只在平台、来源账号与会话等适用范围内比较，不能用一个全局原始消息字符串去重所有平台。

群聊优先使用可靠来源群标识与账号范围；私聊优先使用可靠参与账号关系或来源会话标识。已证明相同的来源身份可以命中现有会话；只有标题相同、昵称相同或可疑账号后缀相似时，先让用户选择目标或确认身份，不静默归并。

当文件明确提供一致的导出者或本人发送标记时可预填本人候选；冲突时保留未确认并继续提供普通阅读。个人统计和分析必须等待身份确认。未知身份不得使用“我”替代显示名称。

例如，两个联系人都叫小林，来源账号不同，必须是不同成员；两台电脑导出同一个已可靠识别的私聊，则映射到同一正式会话。

## 6. 解析器复用与维护

本轮以固定上游提交为参考，维护解析模块、共享类型中必要部分和文件解析依赖；将其统一输出转换为 whomi 模型。原生加速可保留为后续性能选项，首期必须明确实际采用路径的功能覆盖与内存边界，不能因可选加速不可用而静默缩减格式能力。

不整体引入 ChatLab 的数据库管理、会话自动匹配、统计、模型、联系人画像或完整服务层。任何额外模块确有必要时，应说明其提供的能力与依赖，再按需纳入。

每个格式模块提供：格式标识与版本、扩展名及内容特征、单会话或多会话能力、来源标识规则、流式或受限全量解析能力、输出和警告。识别不能只看扩展名；冲突候选要记录选择依据，不把识别成功当成内容校验通过。

例如，`manifest.json` 是 SIWX 导出清单，不应成为一段聊天；目录中 `.jpg` 也不应被作为消息文件解析。

### 6.1 依赖与许可

ChatLab 所核查提交的根许可证为 GNU Affero 通用公共许可证第三版，简称 AGPL-3.0。实际取得代码前记录来源文件、提交、版权、适用许可和改动，不把独立维护解释成可以移除原许可义务。

本轮未选择整个 whomi 的公开发布许可证。复用与集成计划必须核对所取模块及依赖的许可适用范围；若无法满足，不得默默改为从零重写或引入整个上游产品，应提交具体替代方案供用户选择。公开分发前须完成整体许可兼容性确认；本设计不作法律结论。

### 6.2 支持验证合同

每种声明支持的格式至少检查：会话边界、成员与本人候选、时间、消息类型、正文换行、原始标识与回复、未知类型、空内容、多会话拆分、坏记录、重复导入和不完整第二份导出。使用虚构夹具和允许复用的上游夹具，不将真实聊天复制进仓库。

格式不具备某字段时，明示能力缺失而非捏造。例如没有头像或附件的记录仍可导入；不能因此显示已成功读取图片或已完整恢复回复关系。

## 7. 导入流程与校验

### 7.1 来源选择与目录

主进程通过系统对话框或拖放授权建立来源句柄；目录只扫描用户主动选择的根目录。递归发现受支持的入口，跳过不相关文件；不跟随逃出该根目录的链接，不自动读取聊天软件数据库或用户其他目录。

目录可能包含多层包装、多个会话或一个文件中的多个会话；先显示候选名称、数量、格式和目标归属。去除同一入口通过目录和清单被重复发现的情况，不把任意多个文件合成一个会话。未识别项、扫描限制与损坏项计入报告。

扫描深度、文件数、文件大小、单条消息大小和内存限制必须在实施计划中给出明确值与可操作错误；不得只写“支持任意大文件”。本地 11.1 MB 样本的结构属于必须覆盖的规模证据，不是最大容量承诺。

### 7.2 检查层次

1. 快速检查：来源仍可读、类型可识别、目标资料目录可写、任务不冲突，显示候选范围与阻断项。
2. 完整解析与暂存：读取所选会话，校验必要字段、身份关系、时间表达、原始标识和计数；暂存 whomi 记录、问题与来源指纹，不修改正式消息。
3. 合并前检查：确认目标会话、所需用户身份选择和当前数据库版本；来源在读取中改变则失败，不把两版文件混合成一次导入。最终重复检查在正式事务内执行。

没有目标回复、未知消息类型和附件缺失可以作为警告保留。无法明确归属会话、记录无法解析、发送者无法表达、正文被截断而无明确保留策略等属于阻断项；不能静默跳过后声称完整成功。上游跳过数量必须可观察并核对，否则该格式不能声明满足完整导入合同。

### 7.3 状态与结果

任务状态：准备、扫描、待确认、解析暂存、校验、等待提交、提交、完成、部分完成、失败、已取消。

会话结果分别记录待处理、阻断、暂存完成、提交中、已保存、重复无新增、失败、已取消。任务失败与会话失败不是同一个状态。

例如三个会话中 A 保存成功、B 解析失败、C 没有新增消息，任务报告部分完成；明确列出 A 新增数量、B 错误与操作、C 重复数量，不只显示一个失败通知。

计数分别表达收到、首次有效、重复、异常与写入消息数；转换未知类型是保留，不算丢弃。计数单位与多会话边界保持一致，不用文件头的声明数替代实际解析数量。

## 8. 增量合并与事务

### 8.1 稳定原始消息标识

在已确定的正式会话与来源标识范围内建立唯一约束。已存在原始消息标识时直接计为重复，不比较正文、不覆盖消息、不保存修订；同批次内重复也遵循相同规则。不同会话恰有相同原始标识时不能互相误删。

来源无此标识时：同一个源文件的相同指纹与记录位置可跳过；首次导入保留每条独立来源记录。不同源文件向已有会话增量合并，若格式不能提供可靠关系，则将该会话标记为需要处理，不自动用文本摘要猜测。提示改用含消息标识的导出格式或更正会话归属，首期不附加复杂的人工逐条消歧界面。

例如两个“好”在时间、发送者和内容上相同，但没有稳定标识，不能证明它们是一次发送还是两次发送；首期保守处理，不以丢失消息换取看似完整的去重。

### 8.2 单会话事务

暂存完整通过后，针对一个正式会话开启事务，在事务内确定重复、新增成员与消息、来源定位及本会话导入结果，一起提交。重复消息本体不变；只有新增消息确实需要的成员记录才能随本次事务新增。

分批读取暂存记录、分批执行语句不代表分批提交。一个会话的正式新增要么全部提交，要么回滚；其他会话已经提交的结果保持不变。新会话的创建记录也在该事务中，失败不留下空会话。

例如已有 10,000 条，本次准备新增 500 条，写到第 300 条出现约束错误，回滚后仍为原来的 10,000 条，而不是 10,300 条。

后台统一协调写入；正式提交期间其他写操作排队，读操作是否受影响由实际驱动与日志模式验证。不得在界面进程执行长事务，也不能承诺所有写入都瞬时完成。

### 8.3 提交记录与后处理

业务记录与会话已提交状态同事务保存；任务级汇总由这些持久结果重建。只有事务提交成功后才能通知已保存。

消息数、可用时间范围等可恢复摘要更新放在提交后任务中，并明确待更新、成功和失败。摘要失败时消息保持已保存，提供重试摘要，不错误回报整个导入未保存；普通数据库查询索引是主数据正确提交所必需的结构，不能当成可忽略后处理。

例如关闭程序发生在提交之后、显示成功之前，重新打开仍能查到已保存消息和提交状态；再次导入跳过已有标识，不产生第二份副本。

## 9. 中断与资源边界

| 中断点 | 正式数据状态 | 恢复行为 |
|---|---|---|
| 扫描、解析或校验失败 | 当前会话未修改 | 保存问题摘要，清理暂存；其他候选继续 |
| 事务提交前异常 | 当前会话恢复原状 | 回滚、记录失败；原来会话仍能阅读 |
| 事务中用户取消 | 当前会话不保留半批新增 | 在安全检查点中止并回滚 |
| 提交已完成后取消 | 已保存结果保留 | 停止剩余会话，不把已提交结果标为取消 |
| 提交后摘要失败 | 消息已保存 | 标记摘要待重试，不重新导入 |
| 数据进程异常或应用退出 | 由事务恢复到已提交状态 | 启动检查中断任务，清理未提交暂存，恢复结果 |

后台必须将取消作为任务状态处理，不只关闭进度窗口。磁盘不足、来源文件改变、驱动错误均须有可重试结果，不删除用户原始导出目录。临时区只删除本任务拥有的文件，不能因为一次任务失败清空整个资料目录。

首期不承诺从任意解析字节断点续传；失败会话重试可重新解析，已成功会话及已有消息由重复规则保护。

## 10. 阅读、原文定位与前端衔接

现有 `Conversation`、`ChatMessage` 是前端展示类型，不应直接充当存储模型。当前 `App` 通过完整会话数组查找消息，`ConversationReader` 遍历全部消息；接入时必须迁移为列表摘要、按会话消息页和消息范围查询，避免数据库分页后界面又加载全量数据。

通信桥至少提供：选择来源、扫描候选、启动或取消导入、订阅任务状态、读取会话列表页、读取消息页、按稳定消息编号读取引用范围和前后文、读取或确认本人身份。确切方法签名由计划定义。

- 列表和消息页使用稳定游标，不用超大偏移量逐页跳过所有旧消息。
- 已知时间的阅读游标包含时间与消息编号，时间相同时不漏消息；未知时间的顺序规则单独表达。
- 前端原有字符串标识可由本地整数编号稳定转换，不将可超出 JavaScript 安全整数范围的值直接传成数字。
- 从总览或解惑定位原文时，后台先按消息编号定位再取前后文，不要求前端从第一条翻页找到引用。
- 只有保存成功的会话进入正式列表；首次导入完成后提供打开会话操作，不自动触发分析。
- 保留现有前端设计、封面和开发预览边界；新增进度、失败与身份选择的具体布局在实施前按已有设计风格完成，不为接入重做整套界面。

例如，引用范围在会话第 12,000 条附近，点击原文直接打开对应范围，并允许继续加载前后消息；不向界面传输全部 14,715 条再定位。

用户可见文案只表达状态与操作。示例：`导入失败，请检查文件后重试。`、`消息已保存，统计更新失败。重试统计`、`无法确认这是哪个会话，请选择导入目标。`。技术诊断进入不含正文的开发日志，不把实现讨论写到提示里。

## 11. Spark 与来源删除约束

Spark 不作为画像汇总输入，也不作为已删除原文的替代材料参与后续画像计算。画像依据应来自单独受权限约束的材料与分析记录。

用户删除来源会话后允许保留 Spark 内容；对应引用标记为不可用，保留其来源关系以显示失效状态，不能让旧消息编号指向新数据。卡片场景摘要本身也是保留内容，不能宣称删除会话即删除了所有派生文字。

这约束后续 Spark 存储与删除业务；本里程碑不因此实现 Spark 持久化、分析撤销、画像重算或会话删除菜单。

例如一条 Spark 同时引用 A、B，删除 A 后显示 A 原文不可用，B 仍能打开，Spark 继续展示，但不会作为画像汇总的新输入。

## 12. 验收依据

| 场景 | 必须观察到的结果 |
|---|---|
| 桌面启动、重启 | 原有界面正常；已保存会话仍存在，开发示例不进入正式资料 |
| 实际 SIWX 结构的虚构夹具 | 类型映射明确、消息与计数一致、本人后缀冲突可处理、引用摘要不丢失 |
| 同文件重复导入 | 第二次新增为零；本地消息编号及内容不变 |
| 同标识不同正文 | 保留旧正文，不生成修订，不改变旧引用或附件 |
| 第二台电脑导出缺旧消息 | 已有旧消息保留，只增加未见过的标识 |
| 不同会话相同消息标识 | 分别保存，不跨会话误去重 |
| 无稳定标识或会话歧义 | 不凭昵称或相同正文静默合并；按预检结果处理 |
| 单会话提交故障 | 当前会话无半批新增，其他会话与旧消息保持可读 |
| A 成功、B 失败、C 无新增 | 任务报告部分完成，逐会话结果与正式数据库一致 |
| 提交后通知丢失、重启 | 从正式提交记录恢复已保存状态，重试不重复增加 |
| 单条引用、范围引用与未知时间 | 稳定定位、保留前后文与来源顺序，不捏造日期 |
| 解析集合 | 每个声明支持的模块按共同合同有可复现证据，差异与不支持项准确报告 |
| 大规模虚构数据 | 测量导入、峰值内存、打开会话、翻页与取消，不宣称未经测量的规模上限 |

实施计划明确测试命令、夹具来源、故障注入位置与性能样本。文档阶段只检查设计完整性，不把测试计划写成已通过的结果。

## 13. 实施者可决定的事项

实施计划可以选择文件组织、内部函数名、驱动与工具版本、暂存容器、资源上限、后台进程启动方法、默认页大小和必要索引；选择必须满足本文语义，并记录可验证理由。格式原有时间、身份、内容含义不可由实施者自行猜测。

代码复用引发许可或依赖无法满足、格式集合需缩减、需要新增模型调用或云端服务、无法实现单会话事务保证时，属于方案改变，需要回到用户确认，不能作为普通实现细节跳过。

用户审阅完整设计后，下一步使用 `superpowers:writing-plans` 形成实施计划。本设计不自动授权安装依赖、产品编码、提交外部评论、创建工单或拉取请求。
