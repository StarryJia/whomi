# 对话洞察：按模型容量动态分批并保留日期和关联上下文

GitHub 工单：[#13](https://github.com/StarryJia/whomi/issues/13)；2026-11-15 已发布。

工作编号：I03。以下为待实施需求，不代表功能已经完成。

## 用户场景

以下均为虚构示例：一天有数千条消息，另三天只有几句问候；23:58 提出改期，次日 00:05 才回应。用户希望模型理解连续发生的事，而不是程序强制一天一批、每批生成一个人格结论。

现有字节估算不是精确词元计数。词元是模型计量文本长度的单位，不等于消息条数或汉字数。固定消息数、固定十条重叠或固定百分比，都不能保证完整请求装得下或上下文充分。

## 范围与待办

- [ ] 每次构建请求时，根据所选模型的总上下文、最大输入和最大输出限制计算可用容量。计算包含系统提示、包装、工具描述、承接笔记、补充原文和输出预留，不能只统计新聊天正文。
- [ ] 允许容量配置留空：优先用户配置及可靠模型资料；没有准确值时使用保守批次与余量，不伪造模型上限。
- [ ] 优先适配模型计数接口或匹配分词器；估算与实际服务用量分开标记。只可估算时留余量，不能把字节数作为精确词元数。
- [ ] 按原始顺序和剩余容量动态装批，保留时间、发言者、消息编号和显式回复关系。密集一天可拆批，稀疏多天可合批，不按自然日或固定间隔定义事件。
- [ ] 优先保留完整发言和交流边界。单条过长时按段落或安全片段拆分并保存原消息编号和偏移，所有片段处理并保存后才算覆盖该消息。
- [ ] 用显式回复与 [I04](04-reading-analysis.md) 的未结束事项补充相关原文；相邻背景受独立容量限制，关联材料装不下时分次回读，仍无法确认就保留未知。
- [ ] 所有新原文、补充背景和回读均限制在 I02 冻结的任务范围内。每个顺序阅读批次须推进新原文；重叠和回读不重复计算覆盖。
- [ ] 明确的输入过长拒绝触发有界缩批；保存拆分决定和断点，所有重试计入 I04 的任务总预算。其他错误不无条件当容量不足处理。
- [ ] 保留原任务的已完成进度和统计，恢复任务时不重新计算一套不兼容的片段布局。

容量是硬上限，不要求每次填满；目标阅读长度、估算余量和缩批次数通过验证确定，不将示例数值写死成产品要求。模型服务端键值缓存的专项优化属于后续工作，不作为本项前置条件。

## 验收场景

| 虚构输入或操作 | 可观察结果 |
|---|---|
| 一天消息超过单次容量 | 拆为多批、时间和顺序保持；全部原文最终被覆盖，单日不被强制视为单个事件。 |
| 连续三天只有几句 | 可放入同一批，仍保留各自日期；分批器不制造每日结论。 |
| 周五约定后，八十条闲聊外有人显式回复改到周一 | 能按回复关系补读原约定，不依赖固定十条窗口；两条原文可供同一核查关联。 |
| 日期范围最后一晚提出问题，范围外第二天才回复 | 模型只能得到范围内材料，记录尚未得到回应；不会自动发送范围外内容。 |
| 一条超长消息拆成三个片段，前两个已保存 | 该消息尚不计完整覆盖；第三段保存后只增加一次，重读不再增加。 |
| 模型容量全部留空，服务明确拒绝输入过长 | 有限缩批或明确停止，已保存进度保留；不会无限尝试或漏消息。 |

## 验收标准

- [ ] 正常、未知容量和超长单条三类输入均有明确退出路径；最小片段仍不能容纳时报告实际失败。
- [ ] 完整请求计数包含承接内容；输出预留符合服务限制，推理内容的计量遵循对应服务规则。
- [ ] 稠密、稀疏和跨午夜输入保持时间、归属、编号和消息顺序；模型依据原文理解事件。
- [ ] 冻结范围之外的消息不得进入模型请求；界面原文弹窗的自由浏览不改变此分析权限。
- [ ] 唯一消息全部片段首次处理并保存后才计入进度；重叠、回读、重试和恢复不重复累计。
- [ ] 明确超长拒绝、估算误差和旧任务恢复测试通过；真实用量、缺失用量与估算值可区分。
