# Whomi 从想法到闭环的工作流程草案

2026-11-03 的流程讨论和 2026-11-04 的技术方案保存在这里。日常执行请使用[试行第 1 版](workflow.md)和[想法模板](idea-template.md)，项目入口已写入仓库约定。下文保留提出方案时的讨论，其中技术控制需分别验证并启用。

2026-11-04 补充：[路线确认与代理约束](#路线确认与代理约束)。新增内容也是待确认方案，未启用工具钩子、检查脚本、远端工作流或分支保护。

## 目标与建议

让一个想法从提出到结果始终可追溯：最初想解决什么问题、为什么决定做、做到什么程度、怎样验证、最后学到了什么。每项工作保留一个固定编号和一份主记录，其他文档通过链接关联。

例如，维护者以后在新聊天中说继续第 001 条，执行者先读取这条记录及其方案、验证链接，就能知道关系对照还在讨论、正在实施，还是已经交付等待回看，不必从聊天记录猜测进度。

建议先采用仓库文档作为唯一正式记录来源，复用现有设计、研究与开发计划目录；确认流程后再用项目约定固定入口，必要时增加薄层技能。这里的薄层技能只负责读取状态、引导步骤和维护链接，不另建一套计划存储。

## 固定的六个阶段

下表中的关系对照场景均为假设示例，不是已确认的功能规格或已发生的验证结果。

| 阶段 | 需要完成的事与留下的记录 | 进入下一阶段的条件 | 第 001 条示例 |
|---|---|---|---|
| 1. 记录想法 | 保存编号、日期、原话、用户问题与场景，检查是否已有相同记录 | 用户决定进一步评估；仅保存时停在待评估 | 先记录朋友交流主动、工作中等待指示，不要求立刻设计页面 |
| 2. 评估价值与方案 | 核对当前能力、现成方案、可复用部分、剩余成本、隐私边界及关键不确定性 | 用户决定采纳、暂缓或不采纳；会影响选型的验证先获得同意 | 比较是否可用现有记忆材料支持对照；不知道材料是否足够时先提出小规模验证 |
| 3. 制定产品计划 | 明确本次目标、范围、不做的内容、成功标准、依赖、顺序与回看方式；链接设计和开发计划 | 用户确认方案与实施范围，且已有本次开发授权 | 假设先支持用户选定的两段关系，就同时写明单段材料时的边界；具体范围仍待决定 |
| 4. 实施 | 按确认范围开发，记录分支、实现关联与实际检查结果；维护当前进展和下一步 | 实现达到约定范围，可供验收 | 不只做正常展示，也完成已约定的材料不足处理；新增需求回到评估，不悄悄扩展 |
| 5. 验收与交付 | 对照成功标准记录实际结果、证据与遗留问题；记录交付版本或可用产物 | 技术检查通过、用户体验验收完成，约定产物已交付 | 用双方同意的示例材料检查对照、原文对应和不足情形；界面另按项目要求验收完整流程 |
| 6. 回看与闭环 | 对照最初问题记录效果、证据、局限及后续决定 | 维护者认可结论；未解决事项明确退回、另立关联记录或决定停止 | 用户能否从对照中理解情境差异？若仍只看到笼统标签，回到方案讨论，不能仅因代码完成就关闭 |

闭环是对原问题有明确处置结果，不要求每个想法都实现，也不要求结果一定成功。可以是目标达成、部分达成且剩余事项已有明确处理，或验证后决定停止。后两种必须标明限制与决定，不能写成全面成功。

## 状态、证据与决策

建议主流程状态为：

`待评估 → 评估中 → 待实施 → 实施中 → 待验收 → 待回看 → 已闭环`

- **待评估**包含仅收集的想法；**评估中**包含研究、方案讨论与优先级讨论；**待实施**表示范围和顺序已确认，不自动代表当前已获编码授权。临时阻碍写在当前状态旁，不用模糊的进行中覆盖所有阶段。
- 每次状态变化追加一行日期、原状态、新状态、依据或决定，以及下一步。例如验收失败时从待验收退回实施中，保留失败材料与重试所需信息。
- 任一适用阶段可转为**暂缓**或**不采纳**，记录原因；暂缓还记录重启条件。例如依赖的材料质量不足时暂缓，待出现足够材料后重新评估。重复想法链接到原编号，不创建两套进度。
- 发布与效果分开：主记录另外保存交付版本或产物、交付日期及发布状态。代码合并、安装包构建成功或外部工单关闭，都不能自动推定已交付或已闭环。
- 产品方向、范围、优先级与最终效果结论由维护者决定。执行者可在已授权范围内持续完成常规实现、检查和记录更新，不因每个步骤重新索取同一授权。

## 文档如何衔接

| 保存位置 | 保存什么 | 更新时机 |
|---|---|---|
| 本目录 `ideas/` 中原编号文件 | 该事项的唯一主记录：原意、当前状态、决定、关联资料、下一步、最终结果 | 每次状态或关键决定变化时 |
| 本目录索引 | 编号、标题和链接；如展示状态，必须从主记录同步，不独立裁定 | 新增记录或同步主记录时 |
| 根目录 `ROADMAP.md`，尚未创建 | 已选择的阶段目标、顺序及主记录链接；不重复需求全文 | 规划下一版本或调整优先级时 |
| 现有研究、设计和开发计划目录 | 调研证据、功能范围、界面方案与具体实施步骤；均写明关联编号 | 当前阶段需要详细材料时 |
| 现有验证与发布记录 | 可核查的验收证据、交付版本及限制，由主记录链接 | 验收、交付时 |
| `PRODUCT.md` 与使用指南 | 已验证的当前能力与实际操作 | 交付后按真实范围更新 |

简短记录直接写在主记录，只有内容复杂时才拆文档。例如第 001 条刚提出时保留当前一页已足够；不为六个阶段提前生成六份空文件，也不搬走已有设计与验证记录。

保存到仓库的场景默认使用虚构或去标识材料；私人聊天原文留在授权范围内的本地位置。比如回看真实关系对照时，记录观察结论和受限证据位置即可，不能为了闭环把私人聊天提交到公开仓库。

## 怎样让流程持续执行

建议在确认本草案后依次采用以下措施，以下均尚未实施：

1. **流程文档作为正式规则。** 定稿本文，并在项目 `AGENTS.md` 增加简短入口：接到新想法、规划、实现或验收请求时，先找对应主记录，按其状态工作，结束前写回进展、证据和下一步。例如新聊天说继续关系对照，先核实第 001 条是否已获方案确认。
2. **提供渐进填写的模板。** 刚提出时只填问题和场景；进入计划才补范围与验收；交付时才补版本与效果回看。例：不会要求一个尚未评估的想法先填预计工时和发布日期。
3. **按触发时机复查。** 提出想法时收集；规划下一版本时筛选；每轮实施结束时写回；交付时约定回看负责人和触发条件。例：假设维护者试用双方同意的两组示例后回看第 001 条，若没有足够材料则保持待回看并说明原因。这些是工作约定，不是已经创建的自动提醒。
4. **再按需要封装技能。** 用一个本项目技能引导上述流程，复用现有的需求讨论、开发计划和验证技能。例：评估阶段只做研究和范围讨论，不自动调用开发流程；不能把产品路线图技能当作完整闭环管理。

在项目约定和技能中不重复存放完整状态规则，统一引用正式流程文档；主记录承载事实，技能负责执行。换电脑或换聊天后，只要能访问仓库，就能恢复事实；是否自动加载技能取决于所在工具的支持，不能承诺单靠文档就会自动运行。

## 工具选择与复用

| 路径 | 适用性与代价 | 建议 |
|---|---|---|
| 仓库文档、Git 历史与现有技能 | 与 Whomi 当前记录衔接，新增维护最少；筛选和提醒需要约定或后续工具支持 | 现在采用。先用一个功能试行，发现重复步骤后再封装技能 |
| GitHub 工单与项目看板 | 适合多人分工、筛选及事件驱动的状态更新；要明确主记录与看板谁负责哪部分，外部写入需授权 | 出现多人协作需求时再引入，保留编号和证据链接 |
| 单独部署或自行开发管理系统 | 需要迁移记录并维护额外服务；本轮未发现现有记录方式无法承接的必需能力 | 当前不采用，也不开发规划软件 |

官方资料核查于 2026-11-03：[GitHub Projects 内置自动化](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations)可以根据工单关闭、代码变更合并等事件更新状态。本文据此建议，不把看板自动产生的完成状态直接当作产品效果已验证；效果仍由约定证据判断。[Rust 提案生命周期](https://github.com/rust-lang/rfcs#the-rfc-life-cycle)同样区分方案被接受与实现优先级、负责人安排。其他参考见[规划入口](README.md)。

本次建议采用文档作为正式记录，复用已有研究、设计、计划和验证能力；需要补充的是跨阶段的统一记录与入口约定。尚无需自研管理系统，也不默认创建外部工单或定时任务。

## 最小试行与判断标准

建议先以第 001 条做流程试行对象，但目前只验证能否找到原意、状态和下一步，不启动该功能的评估或开发。待维护者决定推进它时，再按相应阶段试行，不为演示流程虚构后续完成记录。

流程本身的判断标准是：另一轮聊天能从主记录恢复工作；下一步及其授权清楚；验收能追溯到最初问题；交付后有明确的效果回看结论或待回看安排。如果要重复维护多个状态、生成无用文档或反复确认已经授权的步骤，就简化流程。

## 路线确认与代理约束

### 怎样确定路线

先确认工作流程，再逐项确认产品方向；采纳本文不会自动批准关系对照的方案或开发。

1. **确认流程基线。** 用户认可后，将本文定稿为流程第 1 版，记录决定日期和适用范围。例如新功能走完整流程，已明确范围的错别字修正可以直接修改、检查并记录，不必再做产品调研。
2. **确认近期目标与顺序。** 规划下一版本时，比较候选事项对目标的帮助、依据、剩余成本和依赖；用户决定当前、接下来、以后分别放什么。比如只有用户决定本轮优先帮助理解关系差异，第 001 条才进入相应计划；记录想法本身不产生这一决定。
3. **批准一份具体范围。** 对准备实施的事项，确认目标、本次包含与排除的行为、验收场景、材料权限、实施边界和方案版本。批准绑定这版范围，而不是批准某个标题下任意后续扩展。例如假设批准只对照用户选定材料，代理不能据此增加后台扫描全部会话。
4. **变更时保留原批准依据。** 改动用户可见行为、数据访问范围或成功标准时，先列出新旧差异和代价，再由用户确认受影响部分；文字修正、进度回写不使整项授权失效。范围内的常规实现与修复继续执行，避免逐文件请示。

关键决定只有几类：采纳与排序、方案与实施范围、验收与效果结论。它们可以在一次清楚的用户指令中同时确认，不强制拆成多轮批准。

### 三层约束及其能力边界

以下是待实施设计，不是当前已生效配置。

| 层次 | 采用的机制 | 能做到什么 | 第 001 条的示例 |
|---|---|---|---|
| 工作指引 | `AGENTS.md` 指向正式流程；项目技能读取主记录并选择当前阶段 | 让代理知道应读取什么、完成什么、写回什么；属于行为指令 | 用户说只评估，代理读取第 001 条并产出研究，不切入功能实现 |
| 执行检查与权限 | 同一套流程校验规则供本地检查与原生工具钩子使用；运行环境限制写入和外部权限 | 对支持的调用提前拒绝；环境权限限制实际可执行动作 | 评估会话没有产品源码写权限；未取得批准的事项不能进入受控开发入口 |
| 合并与交付控制 | 独立执行的持续集成检查、受保护主分支、维护者控制的合并与发布权限 | 不符合检查要求的改动无法进入受保护主线；不能代替需求和体验判断 | 分支上的实现即使可运行，缺少当前范围对应的验收结果也不能交付 |

持续集成指代码变更后自动执行检查。技术控制应检查主记录结构、批准范围版本、实际变更范围和当前代码的验证结果；是否理解了用户的情境差异，仍需按约定场景进行人工判断。文件路径匹配也不能证明功能没有超出语义范围。

### 需要补充的最小实现

- **正式流程、项目入口与模板。** 正式流程只维护一份，`AGENTS.md` 和技能引用它。主记录逐阶段增加机器可读取的字段：编号、状态、范围版本、批准依据、相关方案、实施范围、验收标准及证据、交付信息、下一步。刚提出时不要求填完后续字段。
- **小型流程校验器。** 检查编号唯一、状态转换有效、所需资料齐全、范围批准未过期、实际改动及检查结果与当前事项相符。研究阶段出现产品源码改动时报告失败；实施阶段需要对应的批准范围。产品成功与批准真实性不能由字段齐全来推定。
- **宿主适配。** 项目技能负责步骤引导；Codex 原生工具调用前钩子负责在支持的路径上调用校验器，结束时检查负责提示缺失的交接记录。一般 shell 命令难以仅凭文本推断所有副作用，不能用几个命令关键词替代运行环境权限。
- **远端必需检查。** 后续经授权接入 GitHub Actions，使相关检查成为合并前必需条件，保护 `main`，核对直接推送、管理员绕过和检查来源。检查器及工作流的改动需要单独审查；不能让待验证的改动同时把验证逻辑改成直接通过。

这些是最小构件说明，不是已经拆分并创建的开发任务。继续复用现有测试、类型检查与构建命令，按修改范围选择验证；不再开发一套通用项目管理平台。产品范围、批准与证据属于同一主记录体系，不在技能内保存第二套进度。

### 批准和检查本身也要受保护

在普通文档里写已批准，只是记录，无法单独证明用户确实批准。软约束阶段可记录明确的用户原话及方案版本，便于追溯；若要技术上阻止伪造，应由执行代理无法修改的批准来源或独立的维护者操作授予权限，校验器读取该来源。

例如，代理把待评估改为已批准后立即尝试写源码，受控开发入口应因没有相应的外部授权而拒绝。批准绑定范围版本；改验收标准后旧批准不能继续适用。批准的范围部分与进度、测试记录分开识别，避免每次更新进度都要求重新批准。

执行代理也不能同时拥有修改保护规则、伪造必需检查结果和最终审批的权限。检查程序、运行配置和批准存储须由受保护来源控制；普通仓库中的文件只有在相应保护实际生效后才具备这一作用。若代理仍使用维护者的完整管理员身份，应如实称为有检查的协作流程，不能宣称实现了独立强制审批。单人仓库还需核对提交与审核身份，不能直接要求无法完成的本人批准本人代码变更。

推荐后续产品代码在任务分支实施，受保护 `main` 接收通过检查的改动。本次已获准在 `main` 编辑文档的授权不等于用户已经同意改变未来分支规则；启用前另行明确。外部工单、代码合并请求、仓库设置和发布仍按现有用户授权要求执行；无明确正式提交授权时合并请求只能为草稿。

### 已核查的能力与仍待验证的部分

- [Codex 项目指令](https://learn.chatgpt.com/docs/agent-configuration/agents-md)会加载 `AGENTS.md`；[技能文档](https://learn.chatgpt.com/docs/build-skills)说明技能提供指令、资源和可选脚本。本文将其定位为工作指引，而非操作系统权限控制。
- [Codex 原生钩子](https://learn.chatgpt.com/docs/hooks)支持在工具调用前拒绝部分操作，但工具覆盖有边界；官方还提示回调故障可能未能阻止调用，执行后的检查不能撤销已发生的副作用。因此必须核查本机实际覆盖和故障行为，不能单靠钩子承诺完整阻断。
- [Codex 安全配置示例](https://learn.chatgpt.com/docs/enterprise/security-cookbook)展示了保护钩子程序、限制配置修改的思路。其具体示例不能直接当作 Windows 本机已验证配置；操作系统权限和代理身份仍需单独核对。
- [GitHub 受保护分支](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)支持要求状态检查与审查，并有管理员绕过等配置差异。本轮未读取或修改 Whomi 远端保护设置，不声称远端已受保护。

本机现有 `gstack-freeze` 和 `gstack-guard` 技能文本声明其 gstack 安全钩子未在 Codex CLI 强制执行；这不等于 Codex 没有原生钩子，也不能把调用这两个技能视为已经锁定目录。

### 在正式接入前验证约束是否成立

先提出一次隔离验证，得到用户同意后执行。使用临时示例仓库和无害文件，首轮以约 30 分钟为投入上限；不修改真实 Whomi 代码、批准状态或远端设置。以下均为预期结果，尚未测试：

| 尝试 | 应观察到的结果 |
|---|---|
| 待评估事项请求修改源码，同时允许正常读取与生成研究结果 | 源码保持不变；读取和指定位置的研究输出仍可完成 |
| 代理自行写入已批准，或修改批准过的范围再继续 | 受控入口拒绝缺少可信批准或范围版本不匹配的操作 |
| 从补丁、shell、交互式 shell 后续输入或连接工具尝试同一越界写入 | 逐条核对实际覆盖；未覆盖的入口由权限限制阻止，不能只验证一种工具 |
| 检查程序缺失、故障、超时，或记录结构错误 | 记录真实故障行为；若目标是强约束而动作仍执行，则判定该方案未通过 |
| 已批准事项在许可范围内修改，并通过当前代码所需检查 | 正常完成，不反复请求同一授权 |

若发现宿主不能支持所需控制、存在未封堵路径或需要额外身份权限，停止扩大接入，先报告边界和替代方案；不得把测试失败描述成已启用强约束。远端合并保护另行授权验证，只有确认失败检查确实阻止合并后，才报告该层生效。
