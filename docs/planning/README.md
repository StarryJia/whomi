# Whomi 产品规划与想法池

这里保存产品想法和规划方法。已交付能力见[产品上下文](../../PRODUCT.md)及对应实现记录。

新增或继续事项时，使用[产品工作流程](workflow.md)和[想法模板](idea-template.md)。本机权限与远端合并控制的设计见[技术约束提案](workflow-proposal.md#路线确认与代理约束)。

## 不同记录各自回答什么

| 记录 | 回答的问题 | Whomi 场景示例 |
|---|---|---|
| 产品规划 | 希望帮助谁解决什么问题，哪些方向值得投入 | 讨论怎样帮助用户理解自己在不同关系中的表现，以及是否值得优先投入 |
| 产品路线图 | 已选方向按什么阶段推进，为什么这样排序 | 评估后决定把关系对照放入下一阶段；这是假设示例，目前未作此决定 |
| 想法池 | 有什么值得保留、但还没决定做的想法 | 先记下不同关系中的对照，下次规划时能找到原始场景 |
| 开发计划 | 已确认要做的功能，如何实施和验收 | 确认关系对照的范围后，才安排材料读取、展示与验证步骤 |

保存想法不代表采纳，采纳不代表已经排期，完成设计也不代表功能已实现。

## 建议采用的保存方式

先使用仓库里的 Markdown 文档和 Git 历史：无需新增服务，记录与产品上下文放在一起，也便于后续开发时检索。

- **想法详情**放在本目录的 `ideas/` 中，一条想法一份文件，保存提出日期、原话、用户场景、期望变化、当前状态及待确认事项。例如本次记录保留朋友交流与工作交流的差异，不急着决定页面布局。
- **路线图**等选定阶段目标后再建立根目录 `ROADMAP.md`，按当前、接下来、以后组织，只放目标、简短理由和详情链接。例如关系对照若获采纳，路线图引用第 001 条，不复制整份需求。目前尚未创建这份路线图。
- **功能设计与开发计划**沿用仓库已有的 `docs/designs/`、`docs/superpowers/specs/` 和 `docs/superpowers/plans/`。例如进入开发前，先明确用户能对照哪些材料，再写具体实施步骤。

今后新增想法时先记录；准备下一版本时集中比较用户价值、需求依据、剩余投入和依赖，再由维护者决定采纳、暂缓或放弃。没有证据的成本和效果标为待验证，不编造评分。

只有多人需要分工、筛选和跟踪时，再考虑 GitHub Issues（工单）与 Projects（项目看板）。例如两名贡献者分别负责材料处理与展示时，可以在看板分配负责人并链接同一份设计；无需同时维护两套完整需求。创建或更新外部工单仍需用户明确授权。

## 成熟开源项目的可借鉴做法

以下于 2026-11-03 核查官方流程文档；Whomi 示例是应用这些方法的建议，不是这些项目已经验证过 Whomi 的需求。

| 项目与官方来源 | 核查到的做法 | 对 Whomi 的具体启发 |
|---|---|---|
| [Godot 提案仓库](https://github.com/godotengine/godot-proposals#how-to-suggest-improvements) | 笼统想法进入讨论，充分展开的想法才作为正式提案 | 关系对照先保留问题与场景；明确材料范围和期望结果后，再形成详细设计 |
| [Visual Studio Code 路线图](https://github.com/microsoft/vscode/wiki/Roadmap) | 路线图描述方向，按反馈调整；每月迭代计划提供具体执行内容 | 路线图写帮助用户理解情境差异，开发计划再写本轮交付的范围和验收步骤 |
| [Rust 提案流程](https://github.com/rust-lang/rfcs#the-rfc-life-cycle) | 提案获得认可不等于已安排实现优先级或负责人；实现另有跟踪记录 | 即使认可关系对照值得做，也分别记录是否排期、是否实现，不提前承诺版本 |

建议借用这些项目对状态和文档职责的区分，暂不引入大型项目的完整审批与协作流程。本轮研究的是规划方法，不是选择部署上述产品，也未进行产品功能兼容性验证。

## 可用的技能

技能用于帮助整理、讨论和更新内容，文件才是持续保存的记录。

| 技能 | 适用时机 | Whomi 使用示例 |
|---|---|---|
| [roadmap-update](https://github.com/anthropics/knowledge-work-plugins/blob/main/product-management/skills/roadmap-update/SKILL.md) | 创建或调整路线图，比较新增事项对原安排的影响 | 已有数个候选功能时，讨论加入关系对照后，哪些工作继续、哪些后移 |
| `superpowers:brainstorming`，本机已有 | 展开单个想法，讨论目标、边界与方案 | 准备评估关系对照时，明确用户想看到哪些经历、如何判断有帮助 |
| `superpowers:writing-plans`，本机已有 | 功能方案确认后，形成可执行的开发计划 | 设计确认后列出实施步骤、相关文件与验证方法 |

`roadmap-update` 来自 Anthropic 官方 `knowledge-work-plugins` 仓库。已阅读技能源码；[skills.sh 页面](https://www.skills.sh/anthropics/knowledge-work-plugins/roadmap-update)在本次核查时显示约 3.1 千次安装。安装量仅作采用情况参考，不证明质量或本机兼容性；本次未安装，也未验证其外部项目管理工具连接。

仅为记录这条想法，无需新增技能。以后需要持续维护路线图时，可优先评估 `roadmap-update`；本机已有的两个技能分别服务于需求讨论和开发执行，不替代想法池。

本次采用仓库文档保存，复用现有设计和开发计划目录。无需自行开发规划工具；关系对照本身仍待需求评估和现成方案调研，尚未选定实现路径。
